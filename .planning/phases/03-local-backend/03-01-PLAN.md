# Phase 3 Plan 01: SQLite and Share Permissions

## Goal

在不改变 Viewer 与评论 repository 业务边界的前提下，用 SQLite 管理项目、分享和评论，并由服务端强制 owner、密码、有效期及评论权限。

## Decisions

- 使用本机 Node 22 可用的 `node:sqlite`，不增加原生 npm 驱动；`package.json` 锁定 Node `>=22.12.0`。
- 数据库位于 `storage/blendproof.sqlite`，测试通过 `BLENDPROOF_DB_PATH` 和临时 storage/端口隔离。
- 模型文件仍保留在项目目录；SQLite 保存元数据和关系，不存 GLB/blob。
- owner capability 使用 256-bit 随机值，数据库只保存 SHA-256；项目 ID 不是凭据。
- 分享密码使用 `crypto.scrypt` 加随机 salt；分享 token、密码和 owner capability 均不进入公开 DTO。

## Wave 3A: SQLite foundation

1. 建立 `schema_migrations`、`projects`、`shares`、`comments` 表及索引。
2. 提供服务端 repository，启用 foreign keys、WAL、busy timeout 与事务。
3. 评论 API 从 JSON 切到 SQLite，删除进程内写队列，保持前端合同不变。
4. 增加内存数据库单元测试、并发评论和跨项目作用域测试。

## Wave 3B: Legacy migration

1. 幂等扫描仅含 `model.glb` 的旧项目目录。
2. 导入 manifest、约定的 `share.json` 和 `comments.json`；备份文件不参与迁移。
3. 旧 token 原样保留，默认无密码、无过期、`read_only`。
4. 非法 JSON、重复 token/评论必须报告具体文件并终止对应事务，旧文件不删除。

## Wave 3C: Owner boundary

1. 新项目创建返回一次 owner capability，并只在 SQLite 保存哈希。
2. 项目评论和分享 mutation 必须带 owner capability；无凭据 401、错误凭据 403。
3. 前端本地项目凭据仅用于 owner API，不进入分享 URL、公开响应或日志。
4. `projects.owner_id` 预留未来账户主体；本阶段不接完整登录系统。

## Wave 3D: Share access

1. 一个项目可创建多个分享，支持 password、expiresAt、`read_only | comment` 与 revoke。
2. 密码分享先调用 access endpoint，成功后发路径限定的 HttpOnly cookie。
3. metadata、model、comments 全部统一检查 token、撤销、过期和密码访问态。
4. `comment` 分享只允许访客创建，不能编辑/解决；owner 可管理全部评论。

## Verification

- SQLite 迁移首次执行与重复执行一致，旧 JSON 保持原样。
- A 项目 owner capability 不能读写 B；无/错 capability 均被服务端拒绝。
- 隔离浏览器验证无密码、密码正确/错误、过期前后、撤销、read-only/comment 权限。
- 旧分享链接继续只读打开；公开 DTO 不含 projectId、ownerId、capability 或 hash。
- `source.blend`、数据库、share metadata 不可经文件路由读取。
- `npm run check`、完整 API 测试、生产构建和浏览器控制台全部通过。

## Runtime Constraint

`node:sqlite` 在当前 Node 22 仍输出 ExperimentalWarning；本阶段用于单机开发后端。升级 Node 时必须复跑迁移和 API 套件，阶段 4 直接适配 D1，不把该同步实现带到云端。
