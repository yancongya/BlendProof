# Phase 4 Plan 01: Cloudflare Infrastructure Replacement

## Goal

保持现有 Viewer、上传者流程、分享 URL 和审稿交互不变，把本地 Express/SQLite/文件系统实现替换为可部署的 Workers + D1 + R2。

## Non-negotiable Architecture Contract

- 原始 `.blend` 只能发送到 `localhost`/`127.0.0.1` 的本机转换桥；Worker 不提供 `.blend` 接收路由，R2 永远不保存 `.blend`。
- 本机桥使用一次性配对 nonce，并校验精确 Web Origin；CORS 不是本机桥的唯一授权机制。
- 云端只接收 `model.glb`、经过 allowlist 裁剪的 `manifest.json` 和可选 `thumbnail.webp`。
- 网页与 Worker API 默认同源。分享模型、manifest 和评论全部经 Worker，不启用 `r2.dev`、公开 R2 域名或长期预签名 GET。
- owner capability、分享 token、密码 hash、R2 key 与上传 intent 都不得进入公开 DTO、URL、日志、analytics 或 R2 metadata。

## Upload State Machine

1. `initialize` 创建 `pending` 项目，一次返回 owner capability。
2. owner 使用 capability 创建绑定随机 staging key、方法、Content-Type、SHA-256、大小和短 TTL 的 upload intent。
3. 上传完成后 `finalize` 通过 R2 HEAD/读取验证三类 allowlist 资产、校验和、GLB 头及 manifest schema。
4. D1 条件更新把项目从 `pending/uploading` 切为 `ready`；未 ready 项目不能创建分享。
5. 删除状态为 `deleting/delete_failed`，D1 outbox/清理账本补偿 R2 失败；finalize、删除和清理均使用幂等键及 CAS。
6. 分享过期只阻断该分享，不删除仍由项目或其他分享使用的模型；staging orphan 与删除失败对象分别清理。

## Wave 4A: Adapter Boundary

1. 从当前服务提取 ProjectStorage、ReviewDatabase、ShareAccess 三个业务接口。
2. Local adapters 继续通过现有全部测试，HTTP 合同与公开 DTO 不变。
3. 明确 `.blend` 本机转换边界：云端只接收处理后的 GLB、manifest 与缩略图。
4. 将所有数据库接口统一为 Promise，并从 HTTP 路由提取完整 ShareAccess 策略。

## Wave 4B: Workers Local Runtime

1. 建立独立 Worker 入口、D1 migrations、R2 object key 约定和开发配置。
2. 实现项目初始化、直传凭据、分享访问、评论与清理 API。
3. 使用临时本地 Wrangler/Miniflare 资源运行合同测试，不接触生产数据。
4. Worker 对 multipart `.blend`/`application/x-blender` 返回 415，并断言 D1/R2 零写入。
5. D1 项目记录包含状态、asset version、upload intent/idempotency key、更新时间及清理账本。

## Wave 4C: Web Upload Adapter

1. 浏览器本机转换后上传 GLB/manifest，不上传原始 `.blend`。
2. 根页面和 `/s/:token` 根据环境使用同一 API client。
3. 根页面必须有清晰可见的“打开 .blend”入口和独立上传/转换面板；不能只把入口塞进顶部菜单。
4. 文件选择后先显示本机解析信息：文件名/大小、Scene、Collection、Object、Camera、Material，以及转换与上传所处阶段。
5. 面板显示转换/上传进度、可操作的失败原因、分享状态与到期时间；转换完成后直接复用中央 Viewer 预览。
6. `/s/:token` 保持审稿者界面，不显示上传与 owner capability；上传者和审稿者复用 Viewer 内核而不是复制另一套 Web。
7. 非 loopback 请求不得包含 `.blend` 文件名、MIME、hash 或源字节标记。

## Wave 4D: Deployment Acceptance

1. 经用户授权后创建或绑定真实 Worker、D1、R2 和域名资源。
2. 线上验证 owner 隔离、密码、到期、撤销、评论和对象不可枚举。
3. 配置自动过期清理、额度观测、错误日志和恢复说明。
4. 生产前加入项目创建、上传大小/总量、未完成项目、密码尝试与访客评论速率限制。
5. capability 提供轮换/撤销与丢失说明；启用严格 CSP 并禁止第三方脚本读取 owner 状态。

## Access and Data Safety

- 分享 cookie 使用 `Secure; HttpOnly; SameSite=Lax`、host-only、token 路径限定，寿命不超过分享剩余有效期；HMAC 密钥使用 Worker Secret 并支持轮换。
- mutation 校验精确 Origin 与 JSON Content-Type；若未来跨域，只回显 allowlist Origin，启用 credentials 与 `Vary: Origin`，禁止 `*`。
- R2 key 由服务端生成且至少包含 128-bit 随机对象标识；无 list/prefix API，客户端不能提交任意 key。
- 密码分享响应默认 `Cache-Control: private, no-store`；撤销、过期和旧 cookie 必须立即失效，不能依赖 R2 lifecycle 完成即时阻断。
- Internal record、Owner DTO、Public DTO 使用不同类型和显式序列化器；manifest 限制大小、深度、数组长度并丢弃未知字段。
- D1/R2 无跨资源事务；每个步骤都要有失败注入、幂等重试、CAS 冲突和补偿测试。

## Verification

- Local 与 Cloud adapters 运行同一合同测试。
- 浏览器给源文件加入唯一标记，确认任何非 loopback 请求均没有 `.blend` 文件名、MIME、hash 或源字节。
- 根页面在无项目、已选文件、转换中、上传中、ready 和失败状态下均有可见上传面板；真实 `.blend` 可生成并展示 Scene/Object/Camera/Material 摘要。
- `/s/:token` 不出现上传控件，且与根页面复用同一 Viewer 交互与渲染能力。
- 线上双浏览器端到端验收通过，控制台与 Worker 日志无未处理错误。
- R2 对象、D1 行和过期清理结果可追踪，且不存在公开数据库或源文件路径。
- 完整 R2 key 无法绕过 Worker；任意 ID/key 探测返回一致 404。
- 上传各步骤、finalize/delete/revoke 并发与定时清理经过失败注入，最终只有完整 ready 项目或可追踪 staging。
- 公开响应递归扫描 forbidden keys；带诱饵字段的 manifest 不会反射内部字段。

## Legacy Cloud Migration

- SQLite→D1/R2 迁移保留 project/share/comment ID、token hash、owner capability hash、权限、到期和撤销状态。
- 只迁移 GLB、裁剪后的 manifest 与缩略图，原始 `.blend` 留在本机。
- 固定旧 token/capability fixture 验证迁移前后合同；重复迁移幂等，失败项目不可访问。

## Authorization Boundary

本地适配器、Worker 代码、迁移和 Miniflare 测试可以直接实施；创建/修改真实 Cloudflare 资源、域名或生产数据前必须使用用户明确提供的账户与目标资源。
